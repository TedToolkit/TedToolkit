## 🎯 Outcome and Scope

Prepare the existing libraries as verified, publishable NuGet packages consumable by independent repositories. The final package set is `TedToolkit.CodeAnalysis`, `TedToolkit.ModularPipelines.Build`, and `TedToolkit.ModularPipelines.Combine`. CodeAnalysis does not override consumer rules; it copies only audited Roslynator/StyleCop assets, keeps Sonar as an exact separately licensed dependency, and uses only ADR-002's minimal activation adapter so one consumer reference runs Sonar without copying its DLL. Build provides general build, test, explicit pack/publish-archive, and versioned artifact-manifest capabilities without binding to an AI or notification vendor. Combine can run Build in the same process or consume a manifest from an earlier CI job and internally selects either the GitHub or GitLab provider. GitLab supports arbitrary consumer-supplied instance and API URLs. This change prepares automatic-main publication but performs no live external push as implementation evidence; one human approval enables the release gate, a fresh full main build captures that enablement, and later successful main runs publish automatically.

Scope includes package metadata, project separation, neutral change-description and event models, the cross-job artifact contract, configuration, GitHub/GitLab adapters, unit tests, independent consumer verification, side-effect-free CI dry runs, and release preparation.

Non-goals: no new source-hosting platform; no `TedToolkit.CodeAnalysis.Strict`; no Gemini, OpenAI, Feishu, Slack, Teams, or another concrete AI/notification implementation inside Build or Combine; no TedToolkit-only rule, prompt difference, branch name, or secret embedded in a package; no migration or modification of the external EverythingButTheSink repository; and no live NuGet.org push while implementing or verifying this change.

Compatibility: The libraries do not yet have a stable public NuGet contract, so namespaces and projects may change before the first release. The actual `Build/Program.cs` entry point—not the broader unused module graph in `TedPipeline.ExecuteAsync`—is the repository-host compatibility baseline. `Build/Build.csproj` directly project-references Build and Combine, while external hosts directly package-reference both. Its local command, Release clean/build behavior, branch-push/manual/reusable GitHub triggers and branch validation, `build-output` artifact, and success/failure exit semantics remain functionally equivalent. The existing push trigger is retained for tag events, but tag pushes now resolve to the zero-call `None` profile so automatically created lifecycle tags cannot recursively build or publish; this is an explicit safety correction. The current entry point registers `NugetPushModule` but omits `BumpVersionModule`, `PublishModule`, and `CreateReleaseModule`; with no reliable package producer/import in that graph, the push path can complete with zero packages. Automatic main production/publication of all three packages and creation of the same-version GitHub Release are therefore explicitly approved corrective outcomes, not claims of pre-change observable behavior. The Release uses the normalized version as tag/title and includes links for all published package IDs; exact body whitespace, weekday/timestamp formatting, and repository-description wording are not promises. Internal module types, exact logs/timing, generated model text, mandatory Gemini initialization, legacy raw-output/failure-list files, unpack/re-zip intermediates, and the accidental successful no-package path are not compatibility promises.

## 🧾 Source Intent and Hard Constraints

- Source request: Publish the two libraries to NuGet, remove TedToolkit-only content, follow the Build/Combine separation demonstrated by EverythingButTheSink, abstract GitHub/GitLab, and allow custom GitLab URLs.
- User outcome: Consumers configure their own rules, branches, paths, GitLab addresses, authentication, AI, and notification adapters and can run on GitHub or GitLab CI in either single-job or multi-job workflows.
- External hard constraints: GitLab must not be fixed to GitLab.com; tokens must not leak; published NuGet versions are immutable.

## 🧭 Planned Approach

CodeAnalysis and Build proceed in parallel. P2-NUPIPE-001 begins with the analyzer license/dependency audit, while P2-NUPIPE-002 begins with a shared ModularPipelines-version PoC against both repositories' extension shapes. Build then extracts shared resources, conventions, build modules, a pure date/daily-release-counter policy over neutral consumed-version records, a recoverable temporary MSBuild-version transaction, explicit pack flow, and `PipelineArtifactManifest`. P2-NUPIPE-003 creates Combine and migrates the actual repository host through direct ProjectReferences to both libraries. At cutover, a non-packable one-time command uses the already-present GitHub client boundary and a read-only built-in credential to query authoritative Release history without selecting P2-NUPIPE-004's runtime client. It preserves each accepted exact legacy `tagName` (including counter-zero `.0`), maps it to a normalized package `version`, verifies the tag target against complete local history, writes sorted schema-1 `Build/release-history.v1.json`, and records its hash and non-secret evidence. User acceptance cites the implementation commit containing those exact bytes/hash, after which capture becomes unreachable. The approved schema and generation rules govern that step; the accepted contents become immutable historical evidence rather than a committed current-version file. Runtime version resolution uses no GitHub API. The GitHub main workflow and both manually dispatched lifecycle-recovery actions share one stable repository release concurrency group with `cancel-in-progress: false` and `queue: max`; that workflow-level lock spans version-state read, build, package publication, and final lifecycle-tag mutation, while the queue retains pending triggers. Under that lock, main derives normalized `yyyy.M.d[.<positive-counter>]` from the baseline plus schema-valid annotated package-success and abandoned consumed-version markers, temporarily writes the value to `Directory.Build.props` so SDK-compiled outputs and all three packages receive it, restores the original bytes before manifest/upload, uploads `build-output` without a NuGet credential, and performs automatic package/progress-tag/GitHub-Release publication in a separate gated job. A default-off neutral package-checkpoint hook lets the host create one immutable hash-bearing progress tag after each confirmed NuGet push; retries skip only validated marked packages and never enable duplicate skipping. Its full-set completion callback creates package success before Provider publication, including an all-marked retry. An unmarked duplicate/uncertain result cannot become package success and requires audited abandonment if unresolved. Active pending state blocks new builds; an irrecoverable or unverifiable partial attempt before package success is converted through an audited immutable abandoned marker, while a post-package-success Release failure is finalized through Combine's provider-neutral Release-finalization API without rebuilding or repushing packages. Manual Release recovery creates immutable finalized audit evidence after Release success and before clearing pending, so a hard interruption on either side of that boundary is safely retryable. The temporary `Directory.Build.props` difference is never staged or committed. Each provider work package begins with a client PoC and supplemental ADR approval gate before adding dependencies or implementation. Text generation and notifications are available only through neutral interfaces. Every pipeline-owned remote side effect requires an explicit action switch; package checkpoints additionally require an explicit option plus one trusted implementation, the separate Release-only recovery API requires a direct explicit method invocation, and trusted consumer extensions must own an equivalent opt-in. Finally, validate clean package-only consumer projects with direct Build/Combine PackageReferences, an EverythingButTheSink-derived compatibility fixture, a side-effect-free real GitHub Actions run, and the User-approved isolated GitLab Build/Combine self-test using only generated `.nupkg` files.

The implementation directories, project references, public/internal types, resource composition, configuration keys, and migration order are defined in the [implementation blueprint](implementation-blueprint.md). The [NuGet release contract](nuget-release-contract.md) defines package requirements, and the [test strategy](testing-strategy.md) defines test mapping and commands. All three are implementation constraints of this change.

## ✅ Completion Criteria

- Every package has complete metadata, a package-specific README, license, icon, repository link, and the required symbol-package configuration.
- CodeAnalysis provides copied audited Roslynator/StyleCop analyzers and CodeFixes plus automatic activation of the exact external `SonarAnalyzer.CSharp [10.23.0.137933]` dependency. It contains no Sonar DLL, does not override consumer `.editorconfig` or warning policy, and does not produce a Strict package.
- Build exposes `AddBuildPipeline` and runs its five active local graphs without referencing Combine. Combine exposes `AddStandardPipeline`, maps its active profiles to Build, and runs side-effect-free profiles when no remote action is selected.
- Build's dependencies and public APIs contain no Gemini, OpenAI, `Microsoft.Extensions.AI`, TextCopy, or notification SDK. Build, test, and pack succeed when no `IChangeDescriptionGenerator` is registered.
- Build references no hosting-platform SDK. Combine exposes no hosting SDK type in its public API and selects exactly one internal GitHub or GitLab provider.
- Build uses explicit `dotnet pack` to create nupkg/snupkg outputs and writes a manifest with relative paths, SHA-256 hashes, and no secrets. `ConsumeArtifacts` validates and consumes it in another process without rebuilding.
- Build validates filesystem roots against traversal/link escapes, supports Microsoft.Testing.Platform run/test and conventional VSTest TRX forms, runs publish targets in Publish, and always writes a success/failure manifest last.
- One TedToolkit release version applies to CodeAnalysis, Build, and Combine; the manifest rejects every mixed package version and source-revision mismatch by default.
- A failed manifest remains reportable but authorizes no package push, provider artifact publication, change request, or Release. Consumer-owned CI artifact handoff may still upload/download the failed manifest and safe diagnostics.
- Combine requires no notification service when `IPipelineEventSink` is absent and dispatches neutral events only when notifications are explicitly enabled.
- `Message` performs no PR/MR operation unless `CreateChangeRequest=true`. Combine never mutates repository version files. Build may do so only through the explicitly configured temporary MSBuild-version transaction, which must restore the original bytes before manifest acceptance and has no Git staging/commit capability.
- Every profile/action combination follows the documented compatibility matrix; an enabled forbidden switch fails before commands, secrets, clients, network calls, or sink dispatch.
- NuGet push uses an explicit provider-neutral source and authentication contract. Publication archives carry explicit per-artifact logical names; Release requests carry an explicit tag when required and a target revision matching the validated manifest.
- GitHub supports explicit Enterprise instance/API URLs and repository identity with Actions variables used only as missing-field fallbacks.
- Neutral run, failure, change-request, Release, and event models contain enough provider-free data for consumer notification adapters, with deterministic event order and sink-failure behavior.
- GitLab supports explicit `InstanceUrl` and `ApiUrl`, with tests covering GitLab.com, self-hosted GitLab, and GitLab CI fallback behavior.
- GitHub Release assets and GitLab Generic Packages use provider-specific safe ordering under one neutral release-publication contract.
- The EverythingButTheSink revision pinned by `consumer-baselines.json` supplies shared-behavior evidence. A derived fixture works as an independent consumer using only NuGet packages while preserving local build, cross-job manifest handoff, GitLab MR/Release, NuGet/Generic Package publication, and consumer-owned AI/Feishu adapters; the source repository is not modified.
- Under P2-NUPIPE-003, the current TedToolkit Build host passes the checked-in local, GitHub event/version, two-job release, failure-ownership, and optional-adapter compatibility cases before the monolithic implementation or old binding is removed.
- `dotnet run --project Build/Build.csproj` remains the repository entry point; its non-packable outer bootstrap may compile the host, after which the authoritative pipeline recovers any interrupted version state, cleans and builds `TedToolkit.slnx` in Release, preserves the current tracked-working-tree format semantics when enabled, resolves the runner-local date/daily release count from the checked-in pre-cutover baseline plus complete annotated package-success/abandoned tag history, temporarily rewrites `Directory.Build.props` `<Version>` before pipeline-owned SDK commands, packs all three IDs, restores the exact original bytes before the manifest/upload boundary, and never stages or commits the temporary difference. Build/Combine `AssemblyVersion` and `AssemblyFileVersion` equal `yyyy.M.d.0` or `yyyy.M.d.<counter>`; informational and nuspec versions use the same normalized package-version core. The build job captures the first-external-push gate once; a false-captured artifact remains dry-run-only, and first enablement requires a fresh full build. A separate main job for a true-captured build automatically consumes those exact artifacts, creates an annotated pending reservation, pushes each unmarked package with duplicate skipping disabled, creates its immutable hash-bearing progress marker after confirmed success, publishes the matching annotated package-success tag only after the complete expected progress set, creates the same-version GitHub Release as an intentional corrected repository-release outcome, and then clears pending. “Package success” means that all three immutable NuGet packages have validated completion markers; pending remains until the required repository Release is also finalized. Any pending reservation blocks a new build and must be recovered through its owning publication run, converted before package success by an audited operator to an abandoned consumed-version marker—including when an unmarked remote result is unverifiable—or, after package success only, completed through Combine's provider-neutral audited Release finalization without rebuilding or repushing packages.
- A Build-only independent consumer restores only Build and runs `AddBuildPipeline`; dual-API consumers restore direct same-version Build/Combine `.nupkg` references. All unit, contract, and integration tests in the traceability map pass.
- A side-effect-free GitHub Actions dry run and the User-approved isolated GitLab Build/Combine self-test pass before release readiness. The GitLab evidence executes the canonical template's commands in two independent processes with copied-manifest handoff and fake provider boundaries; a real GitLab runner is not required.
- Every package passes package-content, symbol, dependency-boundary, and local-package-source consumer checks. A failed check prevents release.
