# NuGet Release Contract

> Status: Approved revision. Approved revised design baseline: `be0e9b19941251498807d91088eaa4f8ea4d17a6`. This document forms the implementation contract together with the change README, ADR-001, ADR-002, and the architecture record.

## Package Set and Compatibility

The first release publishes only the following three packages. TedToolkit coordinates CodeAnalysis, Build, and Combine under one calendar release version so one manifest and one automatic main workflow describe the complete immutable package set. Build and Combine initially target `net10.0`; this is not a compatibility commitment to older TFMs. Adding a TFM, splitting providers, adopting independent package lifecycles, or changing the calendar-version strategy requires change-design revision and reapproval.

| PackageId | Assets | Dependency rules |
| --- | --- | --- |
| `TedToolkit.CodeAnalysis` | Analyzer package with no `lib` or `build`; licensed copied Roslynator/StyleCop analyzer, CodeFix, and runtime DLLs under compatible `analyzers/dotnet/.../cs/` paths; exact external `SonarAnalyzer.CSharp [10.23.0.137933]` dependency; and only `buildTransitive/TedToolkit.CodeAnalysis.props` plus `.targets` to activate it | Copied assets must exactly match the resolved PB-04 per-path/per-host preservation inventory. Host-neutral assets remain under `dotnet/cs`; audited upstream Roslyn-versioned variants retain distinct `dotnet/roslyn<major>.<minor>/cs` subtrees and are never flattened. NuGet/SDK selection must resolve exactly one compatible copied set, each retained variant must pass isolated Roslyn-host loading, and the package-only fixture must prove automatic activation of the exact external Sonar DLL. No Sonar DLL or repository project reference appears in the package; any required copied asset/variant or activation failure blocks release rather than permitting partial removal or copied-Sonar fallback |
| `TedToolkit.ModularPipelines.Build` | `net10.0` library, embedded resources, XML documentation, README, and icon | Directly declares ModularPipelines and platform-neutral dependencies; no GitHub/GitLab, Gemini/OpenAI, `Microsoft.Extensions.AI`, TextCopy, or notification SDK |
| `TedToolkit.ModularPipelines.Combine` | `net10.0` library, XML documentation, README, and icon | Exact-version dependency on the same-version Build; `Microsoft.Extensions.Configuration.Abstractions` is the only configuration type intentionally exposed by the optional loader; platform SDKs remain implementation dependencies; no concrete notification SDK |

## Required Nuspec Metadata

Every `.csproj` explicitly produces the following metadata and must not rely on an unimported repository `.props` file:

| Property | Fixed contract |
| --- | --- |
| `PackageId` | Matches the table above |
| `Description`, `Authors`, `PackageTags` | Describe actual public use and contain no private TedToolkit pipeline configuration |
| Build/Combine `PackageLicenseExpression` | `LGPL-3.0-only`; changing to “or later” requires an explicit repository-license change and contract update |
| CodeAnalysis `PackageLicenseFile` | Package-root `LICENSE.txt` describing only the TedToolkit aggregate package; copied upstream licenses/notices and the separately licensed exact Sonar dependency, SSAL license, and corresponding source location go in `THIRD-PARTY-NOTICES.txt`; do not also set `PackageLicenseExpression` |
| `PackageProjectUrl`, `RepositoryUrl`, `RepositoryType` | `https://github.com/TedToolkit/TedToolkit`, the same URL, and `git` |
| `PackageReadmeFile`, `PackageIcon` | Package-specific README and `Icon.jpg` at package root |
| Build/Combine `IncludeSymbols`, `SymbolPackageFormat` | `true`, `snupkg` |
| Build/Combine repository/symbol properties | `PublishRepositoryUrl`, `EmbedUntrackedSources`, `ContinuousIntegrationBuild`, and `Deterministic` are true for release builds; SDK-integrated Source Link, repository commit metadata, and path mapping contain no machine-absolute path |
| CodeAnalysis symbols and SourceLink | Do not produce this repository's `.snupkg` or claim SourceLink for copied third-party analyzers; use asset, dependency, license, and offline-diagnostic checks |

The release entry point passes one version explicitly. Versions are parsed and compared in normalized `NuGetVersion` form. For a TedToolkit release, Build temporarily writes that normalized value to the repository-root `Directory.Build.props` `<Version>` before every pipeline-owned SDK clean/build/test/pack command so compiled and package metadata observe the release version. The outer `dotnet run --project Build/Build.csproj` bootstrap may compile the non-packable host before in-process recovery; it must set `IsPackable=false`, create no package or remote side effect, contribute no manifest artifact, and be followed by the declared clean/rebuild after recovery. CodeAnalysis, Build, and Combine are then packed through three explicit project-level commands with the same version and collected into one manifest. One Build run rejects mixed `PackTarget` versions, a mismatch between the temporary MSBuild version and any target version, compiled-version mismatches, and nuspec/output identity mismatches. Combine's nuspec dependency on Build must be the exact range `[<release-version>]`. The public Build package accepts any valid explicit NuGet version.

For normalized package version `yyyy.M.d`, Build and Combine must contain `AssemblyVersion=yyyy.M.d.0` and `AssemblyFileVersion=yyyy.M.d.0`; for `yyyy.M.d.<counter>`, both equal the four-component version. `AssemblyInformationalVersion` must use the normalized package version as its SemVer core and may contain only SDK-generated build metadata identifying the validated source revision. CodeAnalysis has no package-owned compiled assembly, so only its nuspec version is checked. Because ordinary SDK packing converts a project reference into a minimum-version dependency, Combine's project-local pack target must replace exactly the generated Build dependency metadata with `[$(PackageVersion)]` after project-reference version collection. The PoC selects one exact .NET 10 SDK patch; a root `global.json` then pins it with patch roll-forward disabled, CI installs that same version, and any SDK change requires a reviewed dependency-baseline update plus a fresh PoC. The selected-SDK PoC and package test require exactly one matching dependency and reject the default open range; no candidate Build `PackageReference`, custom nuspec, or post-pack archive rewrite is permitted.

The temporary rewrite is a recoverable file transaction, not a source change. Every active `RunBuild` invocation supplies the target-file and recovery paths; LocalBuild/Validate/Message use a null target version so they recover stale state without beginning a new transaction, while Pack/Publish may supply the target version. None performs no Build call or recovery, preserving its zero-call contract; the next active profile must recover before any producer. After artifact-root cleanup and before mutation, Build stores the original bytes, original hash, temporary hash, and target path in an atomically created root-contained recovery file outside the artifact root and holds an exclusive lock on it for the transaction lifetime. A concurrent invocation fails without recovery or mutation; abrupt process termination releases the lock for a later recovery. The recovery file is never logged, packed, uploaded, or copied into `output/`. Build atomically replaces the target file, preserves the temporary version through every pipeline-owned SDK producer, and restores the exact original bytes on success, handled failure, or cancellation. Restoration and recovery-file removal occur before the final manifest is written. A surviving recovery file is processed as the first in-process operation before artifact cleanup; automatic recovery proceeds only when the target still matches the recorded temporary hash, and any other state fails without overwriting it. Restoration failure makes the run fail and forbids publication. The workflow never stages, commits, or pushes the temporary file difference, and no version-only commit is created. Combine never performs this rewrite.

The repository GitHub workflow preserves the prior `DateTime.Today` calendar scheme by supplying the runner-local `DateOnly`; the public policy does not select a time zone. Counter `0` is the first consumed version for that date, and later package-success or audited abandoned partial attempts increment past the highest consumed counter. The NuGet-normalized package version and post-cutover package-success marker tag are `yyyy.M.d` for counter `0` and `yyyy.M.d.<counter>` for a positive counter through 65534. A further same-day attempt fails before Build because the coordinated counter must remain valid in four-part assembly/file versions. At cutover, a non-packable one-time command uses the already-present GitHub client boundary and a read-only built-in credential—without selecting P2-NUPIPE-004's runtime client—to enumerate every authoritative GitHub Release. It ignores unrelated tag namespaces, accepts non-draft canonical legacy tags in `yyyy.M.d`, `yyyy.M.d.0`, or positive-counter form, preserves each exact `tagName`, maps it to normalized package `version`, verifies its target against complete local tags, writes checked-in non-secret sorted schema-1 `Build/release-history.v1.json`, and records page/total/accepted/ignored counts, the file SHA-256, and secret-free evidence. A draft in the reserved calendar namespace, calendar-like noncanonical/malformed tag, duplicate normalized version or tag, or target conflict fails capture. User acceptance cites the implementation commit containing those exact bytes/hash, after which capture becomes unreachable. Accepted contents are immutable operational history; a later correction requires a separately approved audited data-correction change. Runtime uses no GitHub API. Post-cutover package-success calendar tags use annotation header `tedtoolkit-nuget-success-v1`, while `nuget-abandoned/<version>` markers prevent unsafe reuse without representing package or Release success. Runtime chooses the highest validated consumed counter rather than trusting legacy `releases[0]`: normal monotonic history is equivalent, while incomplete, out-of-order, duplicate, malformed, or manually conflicting history fails safely.

A `nuget-pending/<version>` reservation is an annotated tag targeting the manifest source revision. Its exact LF-delimited message is `tedtoolkit-nuget-pending-v1`, `manifest-sha256=<lowercase-sha256>`, and `run-identity=github:<GITHUB_RUN_ID>`; unknown, missing, or duplicate fields fail. The stable workflow run ID, not its retry-attempt number, owns `build-output`. The host retains this provider/CI metadata and supplies Build only neutral consumed-version records plus `HasActivePublicationReservation`. An active reservation makes a new build return `PublicationRecoveryRequired`; neither the same nor a different revision may rebuild or reuse that version. Recovery reruns the original publication job and must download the original artifact, validate the run identity, source revision, manifest hash, and all file hashes, and use those exact bytes. TedToolkit always uses `SkipDuplicate=false`.

TedToolkit enables Combine's default-off `IPackagePublicationCheckpoint` with `SkipDuplicate=false`; Combine rejects checkpointing plus duplicate skipping before callbacks, secrets, or commands. The checkpoint context contains the validated manifest SHA-256/source revision/version plus ordinal-ignore-case-unique exact package IDs, nupkg hashes, and sibling snupkg hashes. After each deterministic package command returns confirmed success, the host checkpoint creates immutable annotated `nuget-package/<version>/<lowercase-package-id>` at the same revision. The tag segment is the exact PackageId converted with `ToLowerInvariant()` and must pass Git ref-format validation before publication. Its exact LF-delimited fields are `tedtoolkit-nuget-package-v1`, `package-id=<exact-nuspec-id>`, `package-sha256=<lowercase-sha256>`, `symbol-sha256=<lowercase-sha256-or-none>`, `manifest-sha256=<lowercase-sha256>`, and the matching `run-identity=...`. On retry, Combine calls the checkpoint before resolving the NuGet secret, validates the returned subset, skips matching marked packages, and pushes only unmarked packages with duplicate skipping still disabled. NuGet credentials are resolved only when that remaining list is non-empty. It records each confirmed push before the next command. Unknown/duplicate/case-conflicting IDs, missing/unknown/duplicate fields, target/hash/run mismatch, callback failure, or an unmarked duplicate/uncertain result fails. An unmarked duplicate never authorizes a progress or package-success marker.

Main checkout fetches complete tags and validates the pre-cutover baseline. Every main version-resolving workflow, its publication continuation, and each manually dispatched `FinalizeRelease` or `AbandonPublication` action uses the same stable repository-scoped workflow concurrency group with `cancel-in-progress: false` and `queue: max`; the lock is acquired before lifecycle-state read and remains held until final lifecycle-tag mutation or cleanup, and queued triggers are retained instead of replacing the prior pending run. Before creating pending, the publication job validates the exact version's lifecycle: matching package-success without pending returns already completed with zero mutation, and matching abandoned without pending returns already abandoned with zero mutation. Otherwise it creates/reuses the annotated pending tag before the first package, validates/skips already marked packages, pushes and records each remaining package, then calls the checkpoint completion method. Completion revalidates all three expected progress tags and creates/reuses the package-success same-version annotated marker at the manifest revision with the same manifest SHA-256/run identity, including when a retry began with all package IDs already completed. Combine may create/reuse the required GitHub Release only after completion returns successfully, then the host deletes pending. The package-success marker means all three immutable packages have confirmed progress evidence; it does not alone prove repository Release completion, so pending remains until finalization succeeds. A failure before the package-success marker keeps pending and creates no package-success marker. If the package-success marker exists with pending, a retry resolves no NuGet credential and pushes no package: it validates the complete progress set and annotation, creates/reuses the GitHub Release if missing, then deletes pending. If the original manifest artifact expired after the package-success marker, the audited TedToolkit host validates matching immutable package-success/pending tag target and metadata, constructs an empty-artifact neutral release request, and calls Combine's `IReleaseFinalizer`; no GitHub SDK/API implementation exists in the host, and no package is rebuilt or pushed. After Release success it creates immutable annotated `nuget-finalized/<version>` audit evidence and only then deletes pending. Matching finalized-plus-package-success-plus-pending cleanup resolves no NuGet or provider credential and deletes pending only after validating every marker field. Matching abandoned-plus-pending cleanup likewise resolves neither credential and only deletes pending after validating the abandoned marker. Retrying either audited recovery action after its pending cleanup validates the applicable package-success-only, finalized-plus-success-only, or abandoned-only terminal state and returns without recreating pending or calling a provider. Any metadata, progress-set, or revision mismatch fails without moving a tag. Combine keeps Release creation generally optional, but the TedToolkit host enables it as an approved correction to the current entry point; the Release does not advance the counter itself. The exact dependency range follows the official [NuGet version syntax](https://learn.microsoft.com/en-us/nuget/concepts/package-versioning).

If the owning run's original artifact is irrecoverable or an unmarked package has unverifiable duplicate/uncertain remote state before a package-success marker exists, an explicitly audited operator must not rebuild the reserved version. The operator creates immutable annotated `nuget-abandoned/<version>` at the same target revision with the exact LF-delimited fields `tedtoolkit-nuget-abandoned-v1`, the pending tag's `manifest-sha256=...` and `run-identity=...`, and `audit-reference=<opaque-id>`, pushes it, and only then deletes pending. Existing valid package-progress tags remain immutable partial-publication evidence. The opaque ID must match `[A-Za-z0-9][A-Za-z0-9._-]{0,127}` and contain no credential or URL. This performs no further package push, consumes that counter without declaring success, and lets the next build choose a higher version. If the procedure is interrupted after pushing abandoned, a retry validates the target and every copied field, then deletes pending only; publication recovery never pushes an abandoned version. Abandonment is forbidden after a package-success marker, when Release finalization is the only recovery. Missing/unknown/duplicate fields, a mismatched target or copied value, or a pre-existing conflicting abandoned tag fail without deleting pending.

Manual Release-only recovery creates `nuget-finalized/<version>` at the package-success target after `IReleaseFinalizer` succeeds and before pending deletion. Its exact LF-delimited fields are `tedtoolkit-nuget-finalized-v1`, the package-success `manifest-sha256=...` and original `run-identity=...`, `recovery-run-identity=github:<marker-creating-recovery-run-id>`, and `audit-reference=<opaque-id>`. It is immutable, does not consume a second version, and is valid only with matching package success and without abandoned. A retry with finalized plus package success plus pending preserves and validates the marker's original recovery-run identity, requires the same audit reference, does not compare that identity with its new current run ID, and performs only pending deletion; finalized plus package success without pending is terminal. Missing/unknown/duplicate fields, a mismatched target/value, finalized without success, or finalized with abandoned fail without deleting pending. Every handled completion of either manual recovery action also writes one sanitized GitHub job-summary record with the current recovery run identity, action, normalized version, opaque reference, validated pre/post lifecycle states, and disposition; values, URLs, provider responses, and package content outside that allowlist are forbidden. Hard termination may prevent this auxiliary summary, but immutable finalized/abandoned evidence plus retained pending state makes the operation auditable and safely retryable.

The tag names `yyyy.M.d`, `yyyy.M.d.<positive-counter>`, `nuget-pending/<version>`, `nuget-package/<version>/<lowercase-package-id>`, `nuget-finalized/<version>`, and `nuget-abandoned/<version>` are reserved for this automation. Except for exact baseline entries, package-success tags must use LF-delimited `tedtoolkit-nuget-success-v1`, `manifest-sha256=...`, and `run-identity=...` fields matching pending. Package-progress, package-success, finalized, and abandoned tags are never moved or force-pushed. A valid progress tag has at least one matching lifecycle anchor: pending, package success, or abandoned. Pending alone permits a partial progress set; success or abandoned retains evidence after pending deletion; pending plus either success or abandoned is an interrupted cleanup state. Finalized is valid only with package success and without abandoned; finalized plus success plus pending is manual-finalization cleanup, while finalized plus success without pending is terminal. Package success and abandoned are mutually exclusive. A progress tag without an anchor, finalized without success, finalized with abandoned, both success and abandoned, or any target/field mismatch is a conflict. Pending is deleted only after package-success plus Release cleanup, after finalized audit-marker creation in manual Release recovery, or after the audited abandoned marker has been pushed. Other manual creation/deletion is forbidden.

## Prohibited Package Content

- `appsettings.json`, secrets, tokens, user directories, output directories, or machine-absolute paths;
- root `.editorconfig`, `stylecop.json`, repository-specific complete prompt/configuration copies outside Build's versioned neutral embedded baselines, or repository-specific props;
- `ProjectReference`, a machine-absolute checkout path, or another cross-repository path;
- GitHub, GitLab, Octokit, NGitLab, or equivalent SDK dependencies in Build;
- Gemini, OpenAI, `Microsoft.Extensions.AI`, TextCopy, Feishu, or another concrete AI/notification dependency in Build;
- Feishu, Slack, Teams, email, or another concrete notification dependency in Combine;
- `SonarAnalyzer.CSharp.dll`, any CodeAnalysis `build` asset, or any CodeAnalysis `buildTransitive` asset other than `TedToolkit.CodeAnalysis.props` and `TedToolkit.CodeAnalysis.targets`;
- warning escalation, `.editorconfig`, rulesets, `AdditionalFiles`, rule files, package sources, credentials, unrelated MSBuild behavior, or a Strict variant in CodeAnalysis.

## Non-bypassable Pre-release Checks

1. The checked-in root `global.json` selects the exact approved .NET 10 SDK patch with roll-forward disabled, the executing SDK reported by `dotnet --version` matches it, and CI installs that version. Three project-level `dotnet pack` commands then produce three `.nupkg` files and two Build/Combine `.snupkg` files. All package versions match, and Combine has one exact same-version dependency on Build. A focused selected-SDK pack PoC proves the project-local metadata hook produces `[<release-version>]`; any SDK mismatch, missing/multiple Build item, or fallback minimum range blocks release.
2. ZIP/nuspec/PDB and compiled-assembly inspection verifies metadata, README, icon, prohibited items, deterministic path mapping, no machine-absolute document path, and the exact assembly/file/informational mapping above. Build/Combine checks verify license, symbols, SourceLink, and dependency boundaries. CodeAnalysis separately verifies its license/notices, exact `SonarAnalyzer.CSharp [10.23.0.137933]` dependency, the two permitted activation files, and absence of the Sonar DLL.
3. A package-only CodeAnalysis consumer fixture restores the exact Sonar dependency from a controlled source and triggers a known Sonar diagnostic through the transitive activation adapter. Restore/build success alone does not prove analyzer loading, and consumer-defined severity must still win.
4. Dependency checks verify that Build assembly references and public APIs contain no platform SDK and Combine public APIs contain no platform SDK type.
5. A Build-only independent consumer references only Build and calls `AddBuildPipeline`. Independent consumers use direct same-version `PackageReference` entries to both Build and Combine when they call both API surfaces. Package source mapping resolves all candidate `TedToolkit.*` packages exclusively from the temporary local source and third-party dependencies exclusively from controlled upstream sources. Restore/build must not resolve a main-solution project. The separate in-repository host test instead proves its two direct ProjectReferences.
6. Packages, examples, build logs, and test output contain no secret value. On discovery, stop release and rotate the credential.
7. A version-pinned direct/transitive dependency and license inventory is reviewed. Release restore uses `NuGetAuditMode=all` and `NuGetAuditLevel=moderate`; no moderate, high, or critical advisory and no deprecated dependency is allowed. Any exception requires dated supplemental approval before release.
8. Success, command failure, cancellation, and simulated interrupted-run recovery leave `Directory.Build.props` byte-identical to its pre-run contents. A mismatched recovery state fails without overwriting the file. The exact root-anchored `/.tedtoolkit-release-version.recovery` rule passes `git check-ignore` without introducing a broad ignore pattern. Git status contains no version-only staged or unstaged difference before manifest acceptance or publication.
9. TedToolkit never enables duplicate skipping. It creates a package-progress tag only after confirmed command success. Recovery skips only packages with matching immutable progress markers and pushes unmarked packages with `SkipDuplicate=false`; an unmarked duplicate/uncertain result authorizes no progress or package-success state. A new build is blocked while pending exists. Matching package-success-plus-pending pushes no package; it validates the complete progress set and finalizes the required TedToolkit GitHub Release. When the original artifact has expired, the audited empty-artifact `IReleaseFinalizer` path creates/validates immutable finalized evidence after Release success and before pending deletion; interruption before or after that marker is safely retryable.
10. An irrecoverable original publication artifact or unmarked unverifiable package state can unblock later releases only through the audited abandoned-marker transition. The abandoned version is counted as consumed, authorizes no success, is never reused, preserves any valid progress tags as evidence, and matching abandoned-plus-pending state performs pending-deletion-only cleanup.
11. The current `Build/release-history.v1.json` SHA-256 must equal the User-accepted P2-NUPIPE-003 capture record. Capture evidence proves pagination, normalized Release filtering, complete-tag target verification, and contains no credential or raw authenticated response. Missing acceptance or any later unapproved byte change blocks release.

P2-NUPIPE-001 begins with an audit of every candidate analyzer's license, NOTICE, dependency DLLs, supported Roslyn host range, and copy-versus-external-dependency disposition. No copied analyzer asset may be packed before its inventory entry is approved. Sonar remains an exact separately licensed dependency and must not be copied. Do not copy an upstream package's entire content directory without selection.

This change creates verified publishable packages and automatic-main publication capability but performs no live external push as implementation evidence. A human separately approves the one-time enablement of `NUGET_RELEASE_ENABLED`; the first enabled publication requires a fresh full main build that captures the gate as a Boolean job output. Its publication job trusts only that captured output and never re-reads the variable, so an artifact built while the gate was false remains permanently dry-run-only. After enablement, every later successful main build publishes automatically without per-run approval. NuGet.org organization permissions, signing certificates, and final stable-version approval are outside this work package.

Before final push, a human gate also confirms that each PackageId is available on the target source or owned by the publishing organization. Local fixtures do not need to query NuGet.org.

Implementation evidence must follow the official [`dotnet pack`](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-pack), [`dotnet nuget push`](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-nuget-push), and [SDK-integrated Source Link](https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/8.0/source-link) contracts. Do not add a redundant `Microsoft.SourceLink.GitHub` package solely for this .NET 10 repository.
