# ADR-001: Public Pipeline Packages Use Build, Combine, and Neutral Adapter Boundaries

- Status: Proposed
- Date: 2026-07-29
- Decision owner: User
- Decision scope: Long-term public APIs and dependency direction for the NuGet-ready `TedToolkit.CodeAnalysis` and `TedToolkit.ModularPipelines*` packages.
- Governing principles: None; the repository does not currently contain approved principle documents.
- Related change or work package: [P2-nuget-ready-modular-pipelines](../changes/P2-nuget-ready-modular-pipelines/README.md)
- Supersedes: None
- Superseded by: None

## 📌 Decision at a Glance

Split the pipeline into two new public packages: a general-purpose Build package and an explicit Combine package. Together with the existing CodeAnalysis package, the coordinated TedToolkit release contains three NuGet packages. GitHub and GitLab remain two internal provider implementations inside Combine rather than separate public packages. Neither Build nor Combine depends on Gemini, Feishu, or any other concrete AI or notification service. CI jobs exchange results through a versioned artifact manifest. The repository Build host references both new projects directly, while independent consumers reference both NuGet packages directly. TedToolkit releases CodeAnalysis, Build, and Combine under one coordinated version so one manifest can validate and publish the complete package set. Consumers configure both the GitLab instance URL and API URL, with CI variables used only as fallbacks.

## 🧭 Context and Decision Question

The current single pipeline package directly references GitHub and repository-specific resources, so it cannot be safely reused as a cross-repository NuGet package. EverythingButTheSink provides an existing Shared and Combine design for comparison. Both repositories share branch, directory, AI, `.editorconfig`, and prompt conventions, but their complete resource files are not identical. The goal is to extract the shared conventions from platform coupling while retaining repository-specific differences.

The decision must define how the public packages support GitHub, GitLab.com, and self-hosted GitLab while keeping shared resources and standard branches as overridable defaults. It must not impose a repository-specific difference, AI vendor, notification channel, or single-process execution model on other consumers.

## ✅ Decision

Publish `TedToolkit.CodeAnalysis`, `TedToolkit.ModularPipelines.Build`, and `TedToolkit.ModularPipelines.Combine`. Do not create `TedToolkit.CodeAnalysis.Strict`. Build must not depend on a source-control platform. Combine depends on Build and contains the GitHub/GitHub Enterprise and GitLab/self-hosted GitLab providers. The non-packable repository `Build/Build.csproj` directly `ProjectReference`s both Build and Combine so it can build the source revision that produces them. Independent consumers that call both APIs directly `PackageReference` both packages at the same version rather than relying on Combine's transitive dependency.

Build embeds versioned shared `.editorconfig`, commit-message, and change-request instruction baselines, the `main`/`development` constants, and the standard directory layout. Separate instruction resources prevent commit-only rules from leaking into PR/MR summaries. Consumers retain differences through matching overlays or replacements. Build uses the optional, separately enabled `IChangeDescriptionGenerator` but provides no concrete model. Registration alone is inert. Build also provides a platform-neutral calendar-release version policy over `DailyReleaseVersionRequest`: caller-selected date/source revision, neutral consumed-version records with package-success/abandoned disposition, and an active-reservation Boolean. Provider tag annotations, manifest hashes, CI run identities, and recovery evidence remain outside Build. The policy performs no provider query, chooses no time zone, and does not itself touch the filesystem. Active reservation returns publication-recovery-required rather than a buildable version. A separate provider-neutral temporary MSBuild-version transaction snapshots the exact original bytes, atomically writes the resolved `<Version>` to an explicitly selected root-contained `Directory.Build.props`, keeps that value active through pipeline-owned clean/build/test/pack, and restores the original bytes before the final manifest is written. Recovery paths are supplied for every active RunBuild profile; LocalBuild, Validate, and Message recover without applying a new version, while Pack and Publish may apply one. None invokes no Build input or recovery and therefore remains zero-call; the next active profile recovers before any producer. The non-packable outer `dotnet run` bootstrap is excluded from release artifacts and is followed by the declared clean/rebuild after in-process recovery. Build writes status, typed packages, tests, named publish archives, and failure records to exact schema-1 `PipelineArtifactManifest`; every path is relative to a validated artifact root, every file is hashed, and no secret is recorded. The manifest is always the final Build step after restoration has been attempted, including handled Build failure, while a restoration failure produces a failed result and authorizes no remote mutation. A later Combine publication failure changes the host/pipeline result and exit code but never rewrites the already validated Build manifest. The temporary version difference is never staged or committed; Combine never edits the version file.

Combine can run Build in the same process or read the artifact manifest produced by an earlier CI job. Optional notifications are dispatched through `IPipelineEventSink`; Combine does not reference Feishu, Slack, Teams, or another notification SDK. No message is sent unless a sink is registered and notification execution is explicitly enabled. Each profile has a closed set of legal action switches, and invalid combinations fail before commands, credentials, clients, callbacks, or network calls. Change requests are created or updated only when `CreateChangeRequest=true` under `Message` and have deterministic fallback content when no generator is used. Release publication is available only under `Publish`, uses per-artifact logical names and explicit target revisions, and follows provider-specific ordering: GitHub creates/resumes a draft Release before uploading assets, while GitLab uploads/reuses verified Generic Packages before attaching their links to a Release. Retries query first, reuse only matching bytes, and never silently overwrite mismatches. NuGet publication may additionally enable exactly one trusted provider-neutral `IPackagePublicationCheckpoint`; Combine validates its returned completed-package list before resolving a NuGet credential, records each confirmed push before attempting the next package, and calls its completion method exactly once after the full package set and before provider publication. The checkpoint receives only neutral version/revision/manifest/package identities and hashes. It is default-off, requires duplicate skipping to remain disabled, and is invalid outside an enabled Publish/NuGet action. A separate `IReleaseFinalizer.FinalizeAsync(ReleaseFinalizationOptions, ...)` is the only package path outside pipeline profiles: a direct call explicitly authorizes an empty-artifact Release-only operation, requires exactly the selected provider configuration, and performs no Build, package, artifact, change-request, notification, or tag-cleanup action.

The internal GitHub and GitLab providers expose separate instance and API URLs, explicit repository identity, and authentication modes without token-valued public properties. CI variables fill only missing fields. Logical credential references resolve through public provider-neutral `IPipelineSecretResolver`, whose default reads environment variables and which consumers may replace with a secret store. The platform-scoped Actions and GitLab Job Token modes instead read only their exact built-in CI variable through an internal environment reader. Either path runs only for an enabled owning action. URLs reject query, user information, and fragments and preserve explicit path prefixes. NuGet push has its own API-key or NuGet-config contract rather than borrowing hosting authentication. This ADR does not select either provider client; P2-NUPIPE-004 and P2-NUPIPE-005 each begin with an isolated evidence PoC and User-approved supplemental ADR gate before provider dependencies or implementation are added.

## 💡 Why This Decision Is Appropriate Now

The public release must work across repositories and hosting platforms. Keeping the current design or copying the reference repository would turn one platform and one repository's conventions into implicit requirements for every consumer. Keeping providers internal to Combine isolates SDK types without turning the runtime provider choice into a package-management choice.

Concrete AI and notification adapters stay with consumers, reducing public transitive dependencies. The versioned manifest is the durable boundary between the two pipeline packages and makes the existing EverythingButTheSink CI structure a supported execution mode.

The repository's current non-packable Build host remains the first consumer. Compatibility tests use the actual `Build/Program.cs` module list and preserve its observable local/build/trigger/artifact/exit boundary; they do not treat unused modules registered only by `TedPipeline.ExecuteAsync` as observed behavior. The explicit three-package pack/push and same-version GitHub Release path is an approved corrective replacement for the current implicit no-package path. Host-only AI/clipboard presentation may remain optional consumer behavior without entering either public package. Internal module names, legacy unpacked package folders, raw failure files, and implicit package creation are intentionally not compatibility surfaces.

For the repository GitHub release path, the logical counter is zero for the first consumed runner-local-date version and increments past each later package-success or audited abandoned partial attempt that day. Supplying the runner-local `DateOnly` preserves the current `DateTime.Today` behavior while keeping Build neutral; consumers that want UTC choose it themselves. The normalized NuGet/post-cutover tag form is `yyyy.M.d` when the counter is zero and `yyyy.M.d.<counter>` when it is positive. Before pipeline-owned Build commands run, checkout fetches complete tag history. At cutover, a non-packable one-time migration command uses the repository's already-present GitHub client boundary and a read-only built-in credential to query every authoritative GitHub Release without selecting P2-NUPIPE-004's runtime client. It ignores unrelated namespaces, accepts non-draft canonical legacy tags in `yyyy.M.d`, `yyyy.M.d.0`, or positive-counter form, preserves each exact `tagName`, maps it to a normalized package `version`, verifies its target against complete local tags, writes sorted non-secret schema-1 `Build/release-history.v1.json`, and records page/total/accepted/ignored counts, file hash, and query/verification evidence. A draft in the reserved calendar namespace, calendar-like noncanonical/malformed tag, duplicate normalized version or tag, or target conflict fails capture. User acceptance cites the implementation commit containing the exact baseline/hash; the command is then removed or made unreachable. Schema and generation rules are design-approved; accepted contents become immutable operational history. A later correction requires a separately approved, audited data-correction change rather than redesigning the schema. Post-cutover package-success and abandoned markers are schema-valid annotated tags. The host validates provider-owned metadata, maps only normalized version/target/disposition into neutral consumed-version records, and supplies those records, the date, source revision, and an active-reservation Boolean to Build's pure policy without a runtime GitHub API query. An active reservation blocks a new build and requires recovery of the original publication artifact or audited abandonment. With no active reservation, every new run—including a rerun of an already package-success-tagged revision—chooses one more than the highest consumed counter for that date. This intentionally replaces the legacy `releases[0]` dependency with a validated highest-consumed-counter rule: normal monotonic history is unchanged, while out-of-order, duplicate, malformed, or manually conflicting history fails safely instead of silently selecting a lower counter. Abandoned markers prevent reuse after an irrecoverable partial attempt and never represent package success. Every main version-resolving run and both manually dispatched lifecycle-recovery actions share one stable repository-scoped workflow concurrency group with `cancel-in-progress: false` and `queue: max`. The lock spans lifecycle-state read, build, publication, and final tag mutation, preventing recovery from racing either version reservation or normal publication while retaining queued triggers instead of replacing the prior pending run.

The main build/pack job uses only the read-only checkout credential and resolves one runtime version for all three pack targets. After artifact-root cleanup, it persists a root-contained recovery file outside the artifact root, holds an exclusive lifetime lock on it, atomically replaces only the selected MSBuild `<Version>`, and keeps the temporary value in place while the pipeline-owned SDK commands compile and pack all three projects. A concurrent invocation fails without touching the target; abrupt process termination releases the lock for later recovery. The recovery file is never logged, packed, uploaded, or copied into `output/`. Cleanup restores the exact original bytes on success, handled failure, or cancellation and removes the recovery file before `PipelineArtifactManifest` is written and `output/` is uploaded as CI artifact `build-output`. At the start of a later configured invocation, surviving recovery state from abrupt process termination is processed before artifact cleanup and nested SDK commands. A restoration failure fails the build/pack job. The workflow never stages or commits the temporary difference and does not publish until restoration and manifest validation have succeeded.

The main build/pack job captures the repository-owned `NUGET_RELEASE_ENABLED` gate once as a Boolean job output. A separate main-only publication job runs only after that job succeeds and its captured output is true; it never re-reads the variable, so a false-captured artifact cannot later be upgraded through a publication-only retry. Before the first package it creates an annotated `nuget-pending/<version>` at the manifest source revision whose versioned message records the manifest SHA-256 and stable owning CI run identity. Packages are processed in deterministic ID order with `SkipDuplicate=false`. After each command returns confirmed success, the host creates an immutable annotated `nuget-package/<version>/<lowercase-package-id>` marker at the same revision recording exact package ID, nupkg SHA-256, sibling snupkg SHA-256 or `none`, manifest SHA-256, and run identity. A retry validates and skips packages with matching progress markers, then pushes only unmarked packages with duplicate skipping still disabled. A duplicate for an unmarked package is unverifiable and never authorizes a progress or package-success marker. After all three progress markers validate, checkpoint completion creates/reuses the exact annotated package-success version tag with matching manifest/run fields before Combine creates/reuses the required same-version GitHub Release; the host then deletes pending. “Package success” means all three immutable NuGet packages have validated completion markers; pending remains until repository Release finalization completes. Matching package-success-plus-pending resolves no NuGet credential and performs Release finalization plus pending deletion without rebuilding or pushing packages. If the original artifact is irrecoverable before package success, or an unmarked package has an uncertain/duplicate remote disposition, a separate explicitly audited operator procedure creates immutable `nuget-abandoned/<version>` at the same revision with the copied pending identity and a non-secret audit reference before deleting pending; it pushes no package, never marks the version successful, and causes the next version to increment. Abandonment is forbidden after package success. Matching abandoned-plus-pending after an interrupted cleanup resolves no NuGet/provider credential, performs pending-deletion-only cleanup, and never resumes package publication. If the artifact expires after package success, the host validates the immutable matching tag evidence and calls Combine's provider-neutral Release-finalization API; GitHub access remains inside Combine's selected internal provider. After Release success and before pending deletion, that manual path creates immutable `nuget-finalized/<version>` audit evidence containing the copied manifest/original-run identity, the identity of the recovery run that first created the marker, and an opaque audit reference. A later retry preserves and validates that recorded marker-creating identity rather than comparing it with the retry's current run ID, and matching finalized plus package-success plus pending performs pending cleanup without another provider call. Any metadata, progress-set, or revision mismatch fails without moving a tag or clearing pending. The publication job receives the NuGet credential and a least-privilege built-in GitHub credential only in that job, but resolves each only on a lifecycle path that needs it. Combine keeps Release creation generally optional, but the TedToolkit host enables this intentional corrected repository-release outcome; the Release is not the counter's state store. The gate defaults false until the User approves enabling the first external push; first enablement requires a fresh full main build, after which later successful main runs publish automatically without per-run approval.

Revisit the decision if platform SDKs later provide a stable cross-platform API, only one hosting platform remains supported, or the manifest cannot represent required cross-job outputs.

## ⚖️ Consequences and Accepted Trade-offs

Consumers that only build reference Build. Consumers that need pull/merge requests, releases, or publication orchestration also reference Combine. Consumers must register their own concrete AI or notification adapters when they want those optional capabilities.

Combine carries both hosting-platform SDKs, increasing its size and dependency maintenance cost in exchange for one clear consumer entry point. The versioned manifest becomes the compatibility contract between Build and Combine. Self-hosted GitLab URL validation, Generic Package uploads, token handling, and secret redaction become explicit responsibilities of the internal GitLab provider. `IPackagePublicationCheckpoint` is another public trusted mutation boundary: an explicit option plus exactly one registration authorizes it, and a failure after a remote push can leave an unverifiable unmarked package that requires consumer-owned recovery or abandonment. `IReleaseFinalizer` adds a separate public mutating surface, so direct invocation—not service registration—is its authorization boundary; both providers must pass zero-unrelated-call and exact-target idempotency tests.

Coordinated versioning advances CodeAnalysis even when only pipeline implementation changes. This cost is accepted because the repository release path, manifest schema, automatic main publication, and rollback behavior remain one atomic package-set contract. A future requirement for independent package lifecycles requires a new manifest-set and release-orchestration decision.

## 🛠️ Implementation Handoff

Implementation must preserve the one-way dependency direction, closed profile/action matrix, fully specified neutral public models, explicit publication identifiers and target revisions, provider-neutral NuGet push contract, versioned manifest, and safe defaults defined by the architecture record. The associated P2 change design must be approved before implementing, publishing, or changing the current public API.

## 🔄 Release, Rollback, and Exit

The first public release uses the calendar version selected by the runtime policy. If an adapter, manifest, or publication implementation is defective, stop issuing later versions and leave already-published versions immutable. Consumers may remain on the current monolithic project reference until migration is complete.
